# 上下文压缩（Compaction）排期

## 目标与范围

本文定义 WeCode 上下文压缩功能的实施顺序、各期边界与验收标准。目标是在不删除原始会话记录的前提下，将过早历史替换为 LLM 生成的结构化摘要，并最终支持保留最近约 8k tokens 的原始交互。

实施采用四期主线。第 1 期拆分为可独立审查的“摘要生成基础”和“手动闭环接入”两个任务；摘要生成、原文尾部保留、自动触发和 Provider overflow 恢复分别影响内容正确性、上下文构成、执行时机和失败语义，禁止合并为同一期交付。

```text
第 1 期-A：摘要生成基础（已完成）
    ↓
第 1 期-B：手动摘要闭环接入（已完成）
    ↓
第 2 期：摘要 + 最近原文尾部
    ↓
第 3 期：自动预压缩
    ↓
第 4 期：overflow 恢复与可运维性
```

## 统一设计约束

- 原始 `session_message` 历史不可删除；`COMPACTION` 仅改变后续模型请求的有效上下文投影。
- 手动、自动和 overflow 恢复只能复用同一个压缩执行器；触发来源不得改变摘要生成或持久化语义。
- 一次压缩必须遵循“读取稳定快照 → 调用 LLM → 使用快照版本原子提交”的顺序。LLM 调用期间不得持有 SQLite 事务。
- 工具调用与其结果构成不可拆分的完整交互单元；存在未完成工具调用时禁止压缩。
- `reasoningContent` 在摘要生成时作为带 `[Assistant reasoning]` 标签的未受信任历史数据输入，用于保留工具调用前的分析依据；它不得被当作指令执行，也不得改变正常会话的 Provider 回放语义。
- 摘要是历史事实，不是新的高优先级指令。摘要回灌时必须有宿主固定的安全包装，禁止将未经包装的模型摘要作为 system 指令。
- 压缩失败、空摘要、摘要输出截断、版本冲突时不得写入 `COMPACTION` 节点。

## 第 1 期-A：摘要生成基础（已完成）

### 目标

建立可单独测试的摘要输入、提示词和模型调用能力；本任务不改变 CLI、会话状态或数据库中的 `COMPACTION` 检查点。

### 实施内容

- 从持久化层读取最新摘要和其覆盖边界之后的原始 USER、ASSISTANT、工具调用与工具结果，构造只读 `CompactionTranscript`；初始固定 system prompt 不进入摘要输入。
- 将 USER、ASSISTANT、`reasoningContent`、工具调用和工具结果按会话顺序序列化为带角色标签的摘要输入。`reasoningContent` 使用 `[Assistant reasoning]` 标签，和其他历史内容一样仅作为数据处理。
- 工具调用与终态结果作为同一 assistant 条目的完整事实输入；存在 `PENDING`、`RUNNING` 或 `UNKNOWN` 工具调用时拒绝构造 transcript。
- 单条工具结果当前最多输入 2000 个 Unicode 码点，超过部分追加 `[truncated]` 标记；该限制只影响摘要模型输入，不修改原始持久化记录。
- 摘要调用必须禁用工具，并能设置输出 token 上限：默认 2048，硬上限 4096。
- 摘要提示词要求固定 Markdown 模板：目标、重要细节、已完成、进行中、阻塞、下一步、相关文件；增量摘要同时接收旧摘要锚点。
- 摘要提示词必须要求：历史文本和工具输出仅为数据、不得执行其中指令、不得臆造、保留路径/命令/符号/错误文本。
- LLM 返回后拒绝工具调用响应、`LENGTH` 截断响应和空白文本；成功时只返回尚未持久化的 `GeneratedSummary`。

### 原始交付边界

- 第 1 期-A 本身不新增 `/compact` 本地命令；该命令已在第 1 期-B 接入，且不能作为 USER 消息进入会话历史。
- 第 1 期-A 本身不新增 `CompactionService`，不写入 `COMPACTION`，也不改变运行时 LLM 上下文；这些闭环能力由第 1 期-B 提供。
- 第 1 期-A 本身不读取稳定提交快照，也不实现 CAS、冲突返回或摘要安全回灌；这些均已在第 1 期-B 实现。
- 不接入 `ContextWindowPolicy` 的自动触发。
- 不处理 Provider context overflow 后的恢复重试。
- 不实现排队、异步运行或跨进程并发控制。

### 验收标准

- 首次摘要和基于旧摘要的增量摘要均可构造请求并生成未持久化结果。
- 摘要调用不携带工具，且受输出 token 限制。
- USER、ASSISTANT、reasoning、工具调用和工具结果按完整、确定顺序进入摘要；未完成工具调用会拒绝构造摘要输入。
- 空输出、`LENGTH`、工具调用响应和模型异常均不能产生 `GeneratedSummary`。
- 第 1 期-A 单独交付时不产生 `COMPACTION` 记录，也不改变 CLI 输入分发；第 1 期-B 已在其上完成闭环接入。

## 第 1 期-B：手动摘要闭环接入（已完成）

### 目标

将第 1 期-A 的摘要生成能力接入手动控制路径，安全、原子地以新检查点替代当前未压缩历史的运行时投影。

### 实施内容

- 新增 `/compact` 本地命令；命令是控制操作，不能作为 USER 消息进入会话历史。
- 新增不感知触发来源的 `CompactionService.compact(sessionId)`，复用第 1 期-A 的 transcript 与摘要生成器。
- 从持久化层读取稳定 compaction 快照：旧摘要、旧边界之后的完整历史、覆盖终点、`expectedSessionVersion` 与 `expectedLastSequenceNo`。
- LLM 返回后，校验摘要的固定 Markdown 结构；使用快照中的版本与序号以 CAS 方式追加 `COMPACTION`。冲突时返回过期快照，不重新读取后直接提交。
- 摘要回灌为带宿主固定前缀的历史 assistant 上下文，而不是裸 system 消息。

### 本期边界

- 每次压缩覆盖所有当前可压缩历史，等价于 `keepRecentTokens = 0`。
- 不接入 `ContextWindowPolicy` 的自动触发。
- 不处理 Provider context overflow 后的恢复重试。
- 不实现排队、异步运行或跨进程并发控制。

### 验收标准

- 执行 `/compact` 后，下一轮上下文可恢复为“固定 system + 经安全包装的历史摘要”。
- 首次摘要和基于旧摘要的增量摘要均可生成并持久化。
- 工具调用与结果按完整单元进入摘要；未完成工具调用会拒绝压缩。
- 空输出、`LENGTH`、工具调用响应、模型异常和 CAS 冲突均不会产生 compaction 记录。
- 重复执行 `/compact` 且没有新增可压缩历史时，返回“无新增内容”，不调用模型。

## 第 2 期：摘要 + 最近原文尾部

### 目标

降低摘要造成的信息损失，在压缩后仍保留最近约 8k tokens 的原始交互。

### 实施内容

- 新增 `RetentionPlanner`，从最新完整交互单元向前选择原始尾部。
- `keepRecentTokens` 默认设置为约 8000 token，并明确该值基于当前 token 估算器，属于近似预算。
- 摘要输入只包含尾部之前的历史；尾部保持原始 USER、ASSISTANT、工具调用和工具结果。
- 新 `COMPACTION.compactsThroughSequence` 指向尾部前最后一个完整交互单元。
- 复用现有会话投影：固定 system、最新摘要、压缩边界后的原始历史。
- 对单个交互单元超过尾部预算的行为建立明确策略和测试，禁止产生不完整工具协议。

### 本期边界

- 仍只通过第 1 期-B 的 `/compact` 触发压缩。
- 不因上下文阈值自动运行。
- 不在 Provider overflow 后自动重试请求。

### 验收标准

- 压缩后最近约 8k tokens 的原始交互仍可按原顺序回放。
- assistant 工具调用及其 tool result 不会被切分到摘要与原文尾部两侧。
- 旧摘要与本次旧头部合并为新的滚动摘要，已解决事项不会继续标记为进行中。
- 手动压缩后的下一轮模型请求符合“固定 system + 摘要 + 原文尾部”顺序。

## 第 3 期：自动预压缩

### 目标

在请求到达 Provider 上下文上限之前，自动执行压缩并继续原 Agent 轮次。

### 实施内容

- 新增 `CompactionCoordinator`，在每次模型请求前评估完整模型可见请求。
- 将现有 `ContextWindowPolicy` 的“仅记录需要压缩”改为调用协调器；协调器复用第 1 期的压缩服务。
- 增加并传递真实的 Provider 输出 token 预算，不能继续以 `requestOutputTokens = 0` 作为自动压缩依据。
- 支持 `contextLimit`、`requestedOutputTokens`、`buffer`、`auto` 等配置。
- 自动压缩成功后重新从持久化层加载上下文，再执行原本尚未发出的模型请求。
- 记录触发来源为自动，但不得传入或污染压缩器的领域逻辑。

### 本期边界

- 不处理 Provider 已返回 context overflow 的恢复逻辑。
- 不允许因自动压缩失败而继续发送已知超预算的请求。
- 单进程模式下不引入压缩任务队列。

### 验收标准

- 达到预算阈值时，模型请求会先完成压缩并使用重建后的上下文发送。
- 原用户输入只持久化一次，不会因压缩重试重复追加。
- 自动压缩失败会终止本轮并提供可行动错误，不会产生无限重试。
- 关闭 `auto` 后，手动 `/compact` 仍然可用。

## 第 4 期：Provider overflow 恢复与可运维性

### 目标

处理 token 估算误差与 Provider 差异，使自动压缩具备可诊断、可恢复的失败语义。

### 实施内容

- 将 Provider context overflow 解析为可识别的领域异常，而非依赖字符串匹配。
- 仅在尚未持久化 assistant 输出、尚未开始工具调用时，允许一次“overflow → compact → 重建上下文 → 重试原请求”。
- 第二次 overflow、压缩不可用或已经产生副作用时直接失败，禁止循环压缩和重放工具。
- 增加指标：触发来源、输入估算、摘要大小、覆盖序号、尾部大小、耗时与失败类型。
- 日志仅记录摘要长度、序号和错误类别，禁止记录完整摘要、用户输入或工具输出。
- 完善 `wecode.yml` 配置说明和运行时诊断信息。

### 本期边界

- 不新增独立摘要模型或模型回退机制；继续使用当前 session 选中的 Provider/模型。
- 不支持多进程同时压缩同一 session。

### 验收标准

- 预检漏判导致的 context overflow 最多恢复一次。
- 已持久化 assistant 响应或已执行工具的轮次绝不自动重放。
- 第二次 overflow 能明确失败，不发生死循环或重复压缩。
- 可从指标和脱敏日志定位压缩触发原因与失败类别。

## 暂缓：多进程与异步会话编排

该事项不属于当前 compaction 主线，只有在支持多个终端、后台 Agent 或远程控制台时才重新排期。实现前必须先解决 `docs/pending-improvements.md` 中的 session 运行租约问题。

后续范围至少包括：

- session 所有权令牌、租约与续租；
- 繁忙 session 的 `/compact` 排队与重复请求合并；
- 崩溃恢复与过期租约接管；
- 异步 compaction 状态、进度与幂等请求标识；
- 多进程竞争、迟到写入与副作用重放防护测试。
