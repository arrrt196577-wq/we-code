# 待完善事项

本文记录当前阶段明确暂缓、但后续必须重新评估的设计与实现问题。暂缓不代表问题已经解决。

## 上下文窗口 token 估算与输出预算

### 当前阶段决定

- 每次 Agent 请求前使用完整 messages、工具定义、工具调用、工具结果和 reasoning 的 Unicode 字符数，按 `ceil(字符数 / 4)` 估算输入 token。
- 上下文窗口暂时统一固定为 `300,000` token，估算安全余量固定为 `20,000` token。
- 正常 Agent 请求的 `requestOutputTokens` 当前仍为 `0` 的显式占位值；窗口统计只标记 `compactionRequired`，不自动生成新的 compaction。手动 `/compact` 已通过第 1 期-B 的 `CompactionService` 使用摘要生成器，并通过 `ChatRequestOptions` 向 OpenAI 兼容 Provider 发送 `max_tokens=2048`；若数据库中已存在 compaction 检查点，LLM 上下文会使用其摘要和未覆盖尾部。
- 已解析 Provider 响应的官方 `usage` 并写入运行时 `LlmResponse`；当前仍不进行成本统计、会话 token 用量持久化或基于真实用量的预算校准。

### 当前风险

- `字符数 / 4` 对中文、代码、JSON、工具 schema 和 Emoji 的误差不可控，20k 安全余量不能保证不会低估。
- 零输出 token 占位预算不代表模型实际不会生成输出；自动压缩启用前必须发送并约束正常 Agent 请求的输出 token 上限。
- 300k 不是模型能力探测结果；模型或网关实际窗口较小时可能仍返回上下文超限。
- `ChatModel` 的三参数默认实现会忽略 `ChatRequestOptions`；新增 Provider 若未显式覆盖该方法，摘要输出预算会静默失效。

### 重新评估触发条件

- 推进第 2 期原文尾部保留、接入自动压缩、切换 Provider/模型，或出现上下文超限错误。
- 需要显示真实 token 用量、成本统计，或 Provider 可稳定返回官方 usage。

## Compaction 手动闭环后的后续风险

### 当前阶段决定

- 第 1 期-A 提供摘要生成基础：`CompactionTranscript` 从持久化层读取旧摘要及未覆盖历史，`CompactionSummaryGenerator` 以无工具、默认 2048 输出 token 的请求生成未持久化摘要。
- 摘要输入包含 USER、ASSISTANT、`reasoningContent`、工具调用与终态工具结果。reasoning 以 `[Assistant reasoning]` 标签作为未受信任历史数据输入，不作为可执行指令。
- 第 1 期-B 已实现精确匹配、无参数的 `/compact` 本地命令。它不会创建 USER 消息或运行 Agent，而是只对当前活动 session 调用不感知触发来源的 `CompactionService.compact(sessionId)`。
- `CompactionService` 读取携带 `expectedSessionVersion`、`expectedLastSequenceNo` 与覆盖终点的稳定快照；模型调用结束后校验固定 Markdown 结构，并以 CAS 追加 `COMPACTION`。快照过期时丢弃旧摘要，不重新读取后直接提交。
- 摘要以带宿主固定安全前缀的 ASSISTANT 历史消息回灌，而非裸 SYSTEM 指令。当前手动压缩覆盖全部可压缩历史，即 `keepRecentTokens = 0`；`ContextWindowPolicy` 仍只标记需求，尚未自动触发压缩。

### 当前风险

- 当前压缩边界无条件覆盖到快照的 `lastSequenceNo`，没有校验会话是否为 `IDLE`，也没有确认最后一个可压缩单元已经由 ASSISTANT 完整结束。Agent 调用失败后，尚未得到回复的末尾 USER 请求可能在 `INTERRUPTED` 状态下被压入摘要，并在恢复时降格为 ASSISTANT 历史；用户随后只输入“继续”或“重试”时，模型可能不再把原请求视为待执行指令。现有测试允许压缩仅含 SYSTEM + USER 的会话，尚未覆盖该失败场景。
- 单条工具结果在摘要输入中截断为 2000 个 Unicode 码点，但检查点仍声明覆盖对应的完整原始历史。压缩提交后，正常 LLM 投影不会再次读取被覆盖的原始工具结果，因此末尾错误、测试结论或文件路径虽然仍保存在数据库中，却会从后续模型上下文中丢失。
- 摘要安全前缀与模型生成内容被拼接在同一条 ASSISTANT 消息中，该前缀只是普通文本，不构成可信的提示优先级边界。仓库内容或工具输出中的提示注入一旦进入摘要，可能覆盖同消息内的前缀语义并长期影响后续工具调用。
- 当前 Markdown 校验只搜索必需标题是否按顺序出现，并检查非空章节及两个 Next Move 编号；标题前后仍可存在任意文本、额外或重复章节。它不能阻止模型拒答、模板外内容或提示注入文本被持久化，也不能证明摘要事实正确或没有遗漏。
- 同一 session 暂不支持多进程或异步压缩任务。CAS 能阻止旧摘要覆盖新历史，但不能提供运行所有权、排队、重复请求合并或进度反馈。

### 后续解决方向

1. 压缩前要求 session 处于 `IDLE`，并验证覆盖边界落在完整 ASSISTANT 回合之后；末尾 USER 请求、未完成工具回合和其他活动回合必须保留为原始尾部或直接拒绝压缩。
2. 引入按完整交互单元工作的尾部保留策略。对于必须截断的工具结果，至少保留头尾并记录截断元数据；检查点不得静默覆盖未实际提供给摘要模型的重要内容。
3. 在主 Agent 的 SYSTEM prompt 中声明压缩摘要属于不可信历史数据。对摘要执行严格解析，只接受唯一且顺序固定的已知章节，拒绝模板外文本和额外标题，再由宿主重新渲染持久化内容。
4. 增加端到端测试，覆盖 Agent 失败后的 `/compact`、末尾 USER 未回复、超长工具结果、模板外文本、重复标题和摘要提示注入等场景。

### 重新评估触发条件

- 推进第 2 期的原文尾部保留、自动压缩，或 Provider context overflow 恢复。
- 需要调整 reasoning 是否参与摘要、工具结果截断上限、摘要模板字段或事实校验策略。
- 在 `/compact` 面向普通用户稳定发布前，必须至少解决未完成 USER 请求被覆盖和摘要信任边界问题。

## Workspace 类型识别与根路径规范化

### 当前阶段决定

- `WorkspaceResolver` 在 CLI 启动时将当前目录解析为绝对、规范化且已解引用符号链接的真实路径；`WorkspaceStore` 将该路径文本原样持久化，并以同一文本查询。
- 新建工作区的 `type` 固定为 `LOCAL_DIRECTORY`；`trusted_at` 与 `created_at` 在创建时使用同一个当前 UTC epoch milliseconds 值。

### 当前风险

- 非 CLI 调用方仍可直接向 `WorkspaceStore` 传入未规范化路径；同一物理目录的大小写、分隔符、符号链接或等价路径表示仍可能被当作不同 `root_path`，从而绕过文本唯一约束。
- Git 工作区当前不会持久化为独立类型，后续基于类型的行为分支不能仅依赖已有记录。

### 重新评估触发条件

- 需要按 Git 工作区与普通目录执行不同逻辑。
- 需要跨平台稳定识别同一物理目录，或需要处理符号链接。

## Session 多进程并发与运行租约

### 当前阶段决定

- 暂不支持多个 `wecode` 进程同时向同一个 session 提交消息或执行 Agent 轮次。
- 当前阶段不在 `sessions` 表中增加 `run_token`、`run_lease_until` 等运行租约字段。
- `/resume` 仅表示当前交互控制台选中并加载 session，不长期占用或锁定 session。
- 进入 session 后，普通输入触发一次 Agent 轮次；当前实现阶段按单进程、单写入者假设设计。

### 当前风险

- 两个终端同时恢复并写入同一个 session 时，可能交叉追加消息、破坏序号或重复执行工具。
- 仅有 `RUNNING` 状态无法识别具体持有者，也无法可靠区分正常运行与进程崩溃残留。
- 启动时全量执行 `markRunningAsInterrupted()` 可能误伤其他仍在运行的 WeCode 进程，因此它不能作为未来的多进程恢复方案。
- SQLite 事务不能覆盖完整的 LLM 请求和工具执行周期，否则会长时间占用写锁并阻塞其他 session。

### 当前阶段约束

- 产品文档和使用说明必须明确：同一个 session 不支持被多个 WeCode 进程同时操作。
- session 消息追加仍须使用现有 `version` 和 `last_sequence_no` 乐观锁，避免单进程代码中的重复写入被静默接受。
- Agent 轮次开始、正常结束和异常结束仍需维护 `IDLE → RUNNING → IDLE/INTERRUPTED` 状态；暂缓的是跨进程所有权识别，不是状态管理本身。

### 后续解决方向

重新支持该场景时，至少需要：

1. 为 session 增加一次 Agent 轮次级别的所有权令牌和过期时间。
2. 通过条件更新原子领取 session，保证同一时刻只有一个执行者。
3. 执行期间定时续租，正常结束时校验令牌后释放。
4. 租约过期后将遗留执行恢复为 `INTERRUPTED`，并处理未完成的工具调用。
5. 增加双进程竞争、进程崩溃、租约过期接管和旧执行者迟到写入等测试。

### 重新启用的触发条件

出现以下任一需求时，必须先解决本事项：

- 允许用户在多个终端恢复同一个 session。
- 支持后台 Agent、远程控制台或多个 WeCode 实例。
- 支持一个进程退出后由另一个进程自动接管尚未完成的轮次。
- 将 SQLite 会话数据库用于任何多写入者场景。

## Session 恢复与标题生成重试

### 当前阶段决定

- 终端启动后没有活动 session；首条非命令自然语言创建一个 session，并在本进程内持续作为活动 session 使用。
- `/resume` 尚未实现，进程重启后不会自动恢复或列出旧 session。
- 仅根据首条 USER 消息尝试一次模型标题生成。失败、超时或标题校验失败时保留首条消息的截断标题，并且不自动重试。

### 当前风险

- 标题模型调用前后进程崩溃时，当前没有持久化的标题任务状态，因此无法区分“从未尝试”和“尝试失败”。
- 已存在的 `RUNNING` 或 `INTERRUPTED` session 不能从交互界面恢复，用户只能在新 session 中开始对话。

### 重新评估触发条件

- 需要实现 `/resume`、session 列表或上次会话自动恢复。
- 需要标题生成异步执行、失败重试、重新命名建议或标题生成状态展示。
